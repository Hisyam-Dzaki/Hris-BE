# ADR-001 — Incremental infrastructure and tenancy
Date: 2026-11-19 | Status: proposed (owner review)
## Decision
Start with Compose on a single resizable VPS; 2 GB is demo-only until validated, then 4/8/16 GB as measured. Separate persistent data from containers; use local uploads initially with a portable storage interface and off-site encrypted backup. One shared platform and parent domain, optional verified custom domains per tenant. No per-tenant VPS unless contract requires isolation. Go modular monolith and stateless frontend/API; state in PostgreSQL/object storage. Add independent DB node when justified; adopt K3s only when multi-node orchestration is warranted, learning in local sandbox first. Use explicit purchase approval and budget caps.
## Alternatives
Single fixed VPS forever: simple but limits growth and resilience. Swarm: feasible but additional learning/migration path. K3s now: viable for learning, unnecessary production complexity at current stage. Managed Kubernetes: revisit if team/budget/SLA warrants. Per-tenant VPS: costly and operationally complex; dedicated tier only.
## Consequences
Single VPS remains SPOF; local uploads unsuitable for replicated app nodes until migrated. Backups are not HA. HPA does not provision nodes without provider integration. K3s control-plane quorum needs three nodes; database availability remains separate. Review actual costs, load tests, security and recovery before launch or infrastructure changes.
## Revisit triggers
Sustained latency/resource saturation after tuning, storage threshold, customer SLA, or recurring revenue sufficient for cost and support. Owner approves provisioning and production changes.
